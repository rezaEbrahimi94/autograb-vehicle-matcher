# Engineering scope

This local, read-only application applies the relevant engineering principles across its runtime boundaries. The scope is deliberately smaller than a hosted, multi-tenant platform.

| Layer / principle                       | Implementation and verification                                                                                                                                                                                                                                                                                                |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Domain and dependency boundaries        | One matcher and focused interpretation modules; `CatalogueStore` owns SQL; CLI/API use the same factory. Listing-count lookup is injected for unit tests.                                                                                                                                                                      |
| Shared contracts                        | `src/contracts.ts` defines runtime parsers and inferred TypeScript types. Both the HTTP handler and browser client validate requests/responses. There is one contract implementation, rather than independently handwritten browser response shapes.                                                                           |
| Input, configuration and SQL validation | Input shape/size, ports, PostgreSQL URLs, catalogue rows, safe listing counts, fingerprints and response consistency are checked at their boundaries. Invalid operational data raises errors, never a semantic null.                                                                                                           |
| Frontend lifecycle                      | A small typed client validates JSON and errors. The page uses cancellation and request sequence checks to prevent stale responses after edits/new requests; text is rendered with `textContent`. There is no mutation or optimistic-update flow.                                                                               |
| Type and code quality                   | Strict TypeScript includes unchecked-index, exact-optional, unused-code and return/fallthrough checks. Runtime index invariants replace unchecked assumptions. Type-aware ESLint rejects unsafe assignments/calls, explicit `any` and unhandled promises. Prettier formats maintained source; supplied originals are excluded. |
| Safe persistence                        | Parameterized candidate IDs, validated internal schema names, transactional setup, foreign keys and a listing index. Setup refuses to overwrite an existing schema.                                                                                                                                                            |
| Error and async lifecycle               | CLI errors produce nonzero exit status; API errors are sanitized. HTTP async handlers have an explicit rejection boundary. Pool connections and disposable schemas are released after failures.                                                                                                                                |
| Cache integrity                         | Exact-input analysis only; current popularity counts; bounded cache and duplicate coalescing. Source/catalogue fingerprints expose stale server state. Relevant API and browser source files are included in the fingerprint.                                                                                                  |
| Bounded work                            | Token/byte/request limits, four active API requests, capped connection pool, query/acquisition timeouts and a loopback-only HTTP server.                                                                                                                                                                                       |
| Diagnostics and privacy                 | Request IDs, status and duration without descriptions/credentials; source/data hashes in benchmarks. No external telemetry or language-model service.                                                                                                                                                                          |
| Reproducible delivery                   | Exact dependency versions and lockfile; Node/PostgreSQL CI runs typed lint, formatting, browser build, type/unit/SQL/API/CLI checks. Synthetic scale checks use a disposable schema.                                                                                                                                           |

The user requested review against private engineering teaching material. Original frontend and backend sections on contract-driven boundaries, validation, async lifecycle, repository/service separation, error handling, cache invalidation and bounded work were inspected. Only independently worded general practices are used here. No private code, diagrams, transcripts, customer data, paths or organizational configuration is redistributed. This is not a claim of full platform coverage or production certification.

A generated SDK or external schema framework is unnecessary for this one-process, one-client project: shared parsers supply a single source of truth and runtime validation. A framework migration, domain-event bus or generic dependency-injection container would add machinery without another use case. The one intentional lint adjustment permits async adapters whose bodies are synchronous but must satisfy a Promise-returning interface; unsafe-type and promise-handling checks remain enabled. Third-party declaration checking uses TypeScript's `skipLibCheck`; maintained application, browser, script and test code are checked.

Multi-tenant authorization/RLS, billing/webhooks, distributed queues, cloud orchestration, optimistic mutations, internationalization and external-model retries are outside this English-language local challenge. The web demo is not an authenticated public service; external hosting requires a separate security review. Full distributed tracing, calibrated confidence and production capacity claims require deployment data this assessment does not have. Client-boundary tests are automated; full browser end-to-end interaction coverage is not claimed.

CI actions are pinned to verified upstream commits: [checkout](https://github.com/actions/checkout/commit/11bd71901bbe5b1630ceea73d27597364c9af683) and [setup-node](https://github.com/actions/setup-node/commit/49933ea5288caeca8642d1e84afbd3f7d6820020). Review these pins during maintenance. Tooling follows [TypeScript strict indexed access](https://www.typescriptlang.org/tsconfig/noUncheckedIndexedAccess.html), [type-aware ESLint](https://typescript-eslint.io/getting-started/typed-linting/) and [Prettier installation guidance](https://prettier.io/docs/install).

The lint-only `@typescript-eslint/typescript-estree` dependency is overridden to `minimatch` 11.0.8 to address [GHSA-g3hv-75wg-m249](https://github.com/advisories/GHSA-g3hv-75wg-m249). This crosses its declared major range; clean installation, type-aware lint and the tests verify this repository’s use. Remove the override once the upstream tool adopts a patched version. No application matching dependency is replaced.
